### 🟡 P1-1 · 订单存储：JSON 文件 + 无锁 + 非原子写

```python
alipay_service.py:43-48
def _save_orders(orders):
    with open(ORDERS_FILE, 'w', encoding='utf-8') as f:     # ← 直接覆盖，非 temp+rename
        json.dump(orders, f, ...)
```

- **无文件锁**：回调（`/notify`）与轮询（`/order-status`）可并发进入 `_load_orders() → 改 → _save_orders()` 的 read-modify-write，**丢单/丢权益**。
- **非原子写**：进程在 `json.dump` 中途崩溃/被杀 → 文件被截断 → `_load_orders()` 的 `except: return {}` 静默返回空 → **全部历史订单消失**，限购判定失效、恢复码全部作废。
- **`has_user_bought_trial` 每次请求都全量遍历整个 JSON**（O(n)），随订单增长退化。

**修复**：迁移到 SQLite（项目已有空的 `/opt/dsa-mp/data/dsa.db`）或至少引入 `fcntl.flock` + `tempfile + os.replace` 原子写。

### 🟡 P1-2 · 订单号反推 user_id 的兜底逻辑必然是错的

```python
alipay_service.py:159-160
parts = out_trade_no.split('_')
user_id = '_'.join(parts[2:])     # ← 拼不回被截断的部分
```

**证据**：订单号 `aikp_1790145363_phone_108ab87774`，真实 `user_id = phone_108ab8777456`。
因为 `safe_uid = user_id.replace('-','')[:16]`（L75）**截断了 16 字符**，反推只能得到 `phone_108ab87774`（缺 `56`）⇒ 兜底路径会把权益发给一个**不存在的账号**，用户永远看不到会员。

**修复**：订单记录缺失时应**拒绝核销**（返回 `None` 让支付宝重试），而不是猜 user_id；或在 `out_trade_no` 里改用不可反推的随机 ID + 独立映射表。
